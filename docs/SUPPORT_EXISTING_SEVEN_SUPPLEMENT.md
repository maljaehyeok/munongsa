# 기존 7건 상세정보 보완 계획

## 이번 결정 대상

신규 공고 추가가 아니다. 직전 읽기 전용으로 확보한 AWS 상세 JSON 19건을 기준으로, 이미 존재하는 7건에 **39개 구조화 항목**을 덧붙이는 별도 계획이다. 공고 수나 새로운 사실 39건이라는 의미는 아니다. 기존 요약에도 포함된 사실을 개별 항목으로 나누는 경우가 있다.

새 계획: `work/existing-seven-supplement/final-plan.json`.

새 SHA-256: `008aab49260db61dad68d9b861ffb4a0d142e74640fe40241dabda3f9388dea3`.

일치해야 하는 AWS 원본 파일 SHA-256: `c01a7e6a4dd298621bcfa22e840fa849e7b4d8b9d6d02ea58f898aa997f0b451`.

이는 **직전 확보한 스냅샷의 해시**다. 이번에는 AWS를 다시 조회하지 않았다. 실제 적용 직전에 운영 파일을 다시 읽어 일치 여부를 확인해야 한다. 기존 추가용 계획과 `5a09…` 해시는 그대로 보존하며 이번 수정의 승인으로 재사용하지 않는다. 새 계획은 아직 사용자 승인을 받지 않았다.

## 보존 구조와 승인 구분

기존 `records` 19개를 필드·승인·권리·순서까지 변경하지 않는다. 승인 후 새 사실 항목은 상위 `detail_supplements`에 별도로 넣는다. 이 배열에는 원본 레코드 버전, 새 계획 해시, 새 항목별 승인자·참조·시각이 기록된다. 기존 승인을 새 항목 승인으로 복사하지 않는다.

화면은 원래 레코드가 승인 당시 버전과 정확히 같고, 보완 항목의 이용 범위·승인도 유효할 때만 빈 항목을 채워 표시한다. 중복 보완·기존 키 덮어쓰기·미승인 보완·원본 변경은 표시하지 않는다. 기존 내용은 계속 표시한다. 공고 전체 상태·조건 비교·기간 판정은 변경하지 않는다.

GPT 검색과 갱신은 기존 `records`를 그대로 읽으며 보완 배열을 읽지 않는다. 기존 레코드 해시가 변하지 않으므로 승인 근거를 임의 교체하지 않는다. 새 상세정보를 GPT 근거로 자동 편입하지 않는다.

## 실행 도구

`scripts/supplement_support_details.py`의 기본 실행은 읽기 전용 검토다.

```powershell
python -B scripts/supplement_support_details.py --plan work/existing-seven-supplement/final-plan.json --asset work/seven-deploy-preflight/details.json
```

실제 적용에는 `--apply`, **새 계획 해시**, 실제 승인자·승인 기록 참조·비공개 백업 경로를 모두 명시해야 한다. 이번에는 실제 계획으로 적용 명령을 실행하지 않았다. 코드 테스트에서만 명확히 구분한 가상 자료를 사용했다.

안전 조건:

1. 지정된 7개 ID만 허용하며 신규 레코드 추가와 기존 키 변경을 거부한다. 별도 수정 승인 없는 교체 기능은 제공하지 않는다.
2. 정확한 원본 파일 해시와 19개 레코드 각각의 버전이 맞아야 한다. 기본 파일 11건으로는 적용할 수 없다.
3. 적용 전 원본 바이트를 새 백업 디렉터리에 복사하고 해시를 검증한다. 백업 경로는 웹에서 제공되지 않는 비공개 위치를 사용한다.
4. 감사 파일에 승인 참조·계획 해시·변경 전후 파일 해시·보존/추가 필드 목록을 기록한다. 공개 JSON에는 별도 보완 승인 이력만 추가한다. SQLite 승인 DB 기록을 썼다고 간주하지 않는다.
5. 임시 파일을 검증·동기화한 뒤 교체 직전 원본 해시를 다시 확인하고 원자적으로 교체한다. 기존 파일 권한·소유자를 유지한다. 실패 시 기존 파일과 백업을 보존한다.
6. 같은 계획의 정확한 적용 결과가 이미 존재하면 바이트 변경 없이 종료한다. 적용 후 내용이 달라졌다면 성공으로 간주하지 않고 중단한다.
7. 원본 파일·링크 이력·기타 상위 메타데이터를 보존한다. 지정 대상 외 12건과 이전 승인 11건도 그대로 둔다.

## 검증 범위와 적용 전 확인

별도 가상 19건에서 보존·7건 제한·승인 해시·기존 값 변경 차단·백업·원자 교체 실패·중복 실행·변조·GPT 차단을 검사한다. 기존 화면 단위검사에는 승인/미승인 보완·기존 값 유지·기존 버전 변경 시 보완 차단·중복 보완 차단을 추가했다. CSS·전체 화면·동일 원문 전수검사는 반복하지 않는다.

결과: 가상 자료 Python 8개 및 JavaScript 표시·차단 26개가 통과했다. 실제 적용 없이 로컬 미리보기에서 7건의 새 항목 39개가 표시되고 운영 도메인 조건에서는 초안이 차단됨을 확인했다. 캐시한 공개 피드와 7건의 기준 정보도 7/7 일치했다. 이는 현재 서버를 다시 조회하거나 운영 DB 감사 이력을 검증한 결과가 아니다.

AWS 반영 전에 새 계획에 대한 사용자 승인, 실제 운영 파일 해시/백업 경로/파일 권한, 현재 공개 피드의 7건 기준 일치, 현재 웹 코드와 배포 해시를 확인해야 한다. 원본이 달라지면 자동으로 계획 해시를 바꾸거나 이전 승인을 재사용하지 않는다. 승인 DB·서버 내부 감사 이력은 이번 작업에서 확인하지 않았으며 운영 변경·Push·배포는 하지 않는다.
