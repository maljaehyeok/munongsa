# 상세정보 공개 승인: 차단 원인과 결정표

## 결론

새 초안 11건에서 **지금 추가 공개할 수 있는 상세정보는 0건**이다. 이는 전체 서비스의 승인 상세정보가 0건이라는 뜻이 아니다. 현재 저장소의 `assets/support-details.json`에는 기존 승인 자료 11건이 있고, 이번 초안과 겹치는 4건도 그 안에 이미 존재한다. 이번에는 기존 승인 항목을 그대로 유지한다.

기존 공식 원문 11건의 제목·본문 대조 결과는 재사용한다. 원문이나 화면을 다시 전수 조회하지 않았다. 공고 전체가 허위이거나 출처 불명인 것은 아니며, 제목·기관·링크 안내와 상세 내용 공개는 별도다.

## 누가, 무엇을 승인하는가

- **내부 공개 결정권자:** 프로젝트 역할 분담상 최종 승인자인 사용자. 별도 외부 담당자만 승인할 수 있다는 프로젝트 규칙은 확인되지 않았다. CLI는 승인자의 신원을 인증하는 시스템이 아니므로 Codex가 승인자 이름을 넣어 실행했다고 정당한 승인이 되는 것은 아니다.
- **이용 권한 판단:** 공식 공개 이용 조건으로 허용 범위가 확인되면 그 근거를 사용한다. 그렇지 않으면 실제 권리자의 허락 또는 해당 필드의 별도 이용 근거가 필요하다. 프로젝트 사용자 승인은 제3자 권리를 대신 허락하는 행위가 아니다.
- **운영 실행:** 승인된 계획과 서버 자료를 운영자가 대조한 뒤 수행한다. 서버 DB 승인과 설명용 JSON 승인은 서로 다른 기록이다.

사용자가 한 번에 결정할 내용:

1. 신규 7건의 위 후보 중 공개할 항목, 제외할 항목을 선택한다. 기존 4건은 유지할지, 향후 수정 검토할지 결정한다.
2. 선택한 상세 항목을 표시할 수 있는 이용 조건의 공식 주소·적용 범위 또는 허락 기록을 확인한다. 제목·링크 정책만으로 본문까지 허용됐다고 표시하지 않는다.
3. 제외 항목과 권한 근거를 반영한 **최종 계획 파일의 해시**를 제시받고 “이 해시의 신규 7건/선택 항목 공개를 승인한다”는 명시적 기록을 남긴다. 현재 후보 파일의 포괄 승인을 요청하는 단계는 아니다.
4. 승인 기록의 참조와 승인자 표시를 함께 보존한다. 필드나 계획이 변경되면 해시가 달라지므로 다시 승인받는다.

## 준비한 파일과 실제 실행 방법

로컬 비공개 `work/support-approval-package/`에 기존 결과에서 다음 파일을 분리했다. **승인 상태는 부여하지 않았다.**

- `append-7-plan.json`: 신규 7건의 검토 후보. SHA-256 `26f780f79f18652e043bc8249910d5ab5084cd69d791f39466e507d0a52d083f`.
- `amendment-4-review-only.json`: 기존 4건과 비교할 검토 자료. 기존 추가 전용 CLI에 승인 입력으로 사용하지 않는다.
- `manifest.json`: 후보별 해시, 로컬 기존 자산 보존 해시, 차단 사유. 계획에는 근거 발췌가 포함되므로 비공개 로컬 검토 자료로만 보관하고 Git에서 제외한다. 운영 DB·승인 이력·원문 파일은 복사하지 않았다.

선택·권한 확인으로 후보가 바뀌면 위 해시와 파일을 최종본으로 다시 생성해야 한다. 승인 후 실행 위치는 신규 개발 폴더다. 아래는 **절차 설명용 템플릿이며 이번에는 실행하지 않았다.**

```powershell
python -B scripts/review_support_details.py --plan "<승인된 최종 신규 계획>" --output assets/support-details.json --approve --reviewer "<실제 승인자 표시>" --approval-reference "<명시적 승인 기록 참조>" --approved-plan-sha256 "<사용자가 승인한 최종 계획 SHA-256>" --preserve-sha256 "<실행 직전 기존 상세 JSON SHA-256>"
```

실행 전 기존 JSON을 비공개 경로에 백업한다. 결과 JSON의 `approval`에는 승인자·참조·시각이 남으며, 원래 계획·해시·승인 의사 기록은 별도로 보관한다. 이 명령은 운영 DB 감사 이력을 작성하지 않는다. 승인 시 기존 링크 검증 이력이 사라질 수 있던 코드 문제는 이번에 수정했고, 기존 레코드·상위 메타데이터 보존과 중복 거부를 가상 자료로 검사했다.

## 승인 후에도 남는 기술적 연결

1. 운영 공개 피드에서 7건의 상태와 상세 `basis`를 읽기 전용으로 대조해야 한다. 현재 로컬 미리보기의 공고 상태는 운영 상태 증명이 아니다.
2. 공고가 기본 안내 상태라면 현재 상세 UI는 새 상세를 표시하지 않는다. **항목 단위 공개 승인을 연결하는 제한된 표시 경로**가 필요하다. 승인 전 게이트를 풀거나 공고 전체를 검증 완료로 승격하는 수정은 하지 않았다.
3. GPT 상세 답변은 별도 승인·버전·근거 동기화가 필요하다. JSON이 추가됐다는 이유로 고정 해시를 임의 갱신하거나 승인 조건을 건너뛰지 않는다. 일반 안내 검색은 제목·링크 범위를 유지한다.
4. 배포할 파일의 최종 바이트 해시와 서버 자료 해시를 대조해야 한다. 공개 저장소의 기본 상세 11건이나 빈 공개 피드로 서버 자료를 덮어쓰지 않는다.
5. 이전 웹/API 코드와 상세 JSON을 서버 내부 비공개 경로에 백업하고, 실패 시 변경한 코드·상세 JSON만 복원한다. DB·승인·자동수집·인증서·격리 설정은 변경하지 않는다.

**현재 AWS 반영 준비는 미완료다.** 사용자 승인 하나만 받으면 모든 경로가 끝나는 상태가 아니다. 새 조사나 화면 전수검사 대신 권한 근거·선택 필드·승인·운영 연결이라는 실제 남은 단계만 해결해야 한다.
